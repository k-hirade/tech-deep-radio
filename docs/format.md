# 台本の書き方

ニュースの紹介ではなく、技術そのものを理解させる番組。掛け合いの形は「ゆるコンピュータ科学ラジオ」を参考にしているが、名前・決めぜりふ・台詞は流用しない。

## 登場人物
- **タカミ（T）**: 解説役。その技術に本気で興奮している。結論や驚きを先に見せ、たとえ話で順序立てて説明する。
- **ユウ（Y）**: 聞き手。普段タイプスクリプトを書くエンジニアだが、その分野は素人。疑う、外す、自分の経験を持ち込む、自分の言葉で言い換える。受け身にしない。

## 冒頭（最初の1分）
- 挨拶・番組名・自己紹介・ニュースの紹介から始めない。1行目は、タカミからユウへの投げかけ。
- 投げかけの型（毎回どれか1つ）:
  1. 常識をひっくり返す断言（「AとBって、実は同じものなんですよ」）
  2. 当てさせるクイズ（「何が起きたと思う？」）
  3. 歴史の一場面から入る物語（謎を残して本題へ）
  4. 身近な一瞬を分解する（「この0.2秒の間に何が起きているか」）
  5. 流行語の正体を一言で明かす（「◯◯の正体は、ただの△△でした」）
- ユウは疑う・外す（「いやいや、無理でしょう」）。
- タカミが熱を語る（「これを知ったとき一番衝撃だった。今日はそれを追体験してほしい」）。
- 「イメージをつかむため、厳密さを捨てて単純化する」と断る。
- その日のニュースは、なぜ今この話かを示す程度（1〜2分）にとどめ、終盤の回収に使う。

## 本編
- 前提の確認から積み上げる。ユウが知っているもの（プログラミングの概念）を足場にする。
- 1テーマを深く。章ごとに「核心」を1つ置き、何番目の核心かを宣言する。
- ユウに実際に考えさせる場面を作り、ユウ自身に気づかせる（答えをタカミが全部言わない）。
- たとえ話は1章に1つ以上。エンジニアの日常（コンパイラ、テスト、依存関係、レガシーコード）に結びつける。
- 歴史の事件や人物を入れて、話に起伏をつける。
- 落とし穴・誤解・限界を必ず扱う。未確定の主張は「主張の段階」と明言する。
- 最後に冒頭の問いを回収し、ユウが自分の言葉で答える。タカミが一言で締める。長い締めの挨拶はしない。

## 分量と書式
- 約1.5万〜1.6万字で約40分（解説 speed 1.0 / 聞き手 1.02）。
- 1行1発言。`T|本文` / `Y|本文`。1発言は長くても150字程度。
- 英字は読み間違えやすいので、なるべくカタカナで書く。残す場合は `config/readings.json` に読みを足す。
- 記号・数式・コードは声に出せる言葉に直す。
